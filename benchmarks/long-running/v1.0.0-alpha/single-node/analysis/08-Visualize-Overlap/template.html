Overview — full run, four rows: errors, autovacuum, sampler, p99 latency. Shaded box is the current view; drag to select a range.
  • Bars have a 2px minimum width. A 5-second event on a 7-day axis is far narrower than one pixel, so at wide zoom a bar's width shows presence, not duration. Zoom in before comparing widths.
  • A lane too dense to resolve switches to a coverage profile (its label then reads coverage %): bar height becomes the fraction of that pixel-column's time span that is covered. The sampler lane starts this way — 1872 windows over 7 days cannot be drawn as separate bars, and drawing them at the 2px floor would falsely read as "always busy" when the real duty cycle is 7.7%. Zoom in and the lane reverts to true bars.
  • The autovacuum lane is hatched before 2026-08-03 12:05Z — AWS retains these postgres logs for 3 days only, so vacuum activity in the first two days of the run is unknown, not absent. Overlap percentages for autovacuum are computed only over the covered span.
  • Sampler windows are derived, not logged. long-run-sampler.sh sleeps 300s after each sample, so a window is [t[i], t[i+1] − 300s].
  • Autovacuum start times are also derived: postgres logs on completion, so start = end − elapsed at 1-second log resolution.
  • The latency panel is JMeter-side, at 5-minute resolution — from latency-drift.csv for 01-thunder_oauth_authorization_code_grant / 1000 users. Each point is a whole bucket, so a 2-second error burst is diluted across 300 seconds of ~250k requests: expect a burst to nudge p99, not to spike it. The three percentiles share one ms axis because they share one unit; throughput and error rate are separate views, never a second y-scale.
  • Y is logarithmic by default here — p50 sits at 5 ms and the worst p99 bucket at 3172 ms. On a linear axis fixed to that peak, p50 and p95 are a flat line on the floor. Untick Log Y for a linear axis; the label under the panel name always says which is in force.
  • The error-rate view is JMeter's own, and it is not the error lane. Its one large spike (6.3% of the 08-01 08:40Z bucket) is the RDS minor-version upgrade, which step 03 removes from the error lane as planned downtime. The nine remaining buckets with any errors at all sit at 0.01%.
  • Latency buckets stop being contiguous after 2026-08-07 04:05Z — 22 buckets are missing across 12 breaks, all between 04:05Z and 07:00Z. The buckets on either side carry a normal ~248k requests, so this is missing measurement data rather than a visible stall; the cause is not established here. The line breaks at a missing bucket rather than bridging it, so a gap reads as absent data, not as flat latency.
  • The RDS metric panel shares this x-axis but has its own y-axis — one metric at a time, never two scales on one plot. At 1-minute resolution a pixel column usually holds several samples, so the band is that column's min–max and the line is its mean. Y is fixed to the whole run's peak by default so zooming doesn't silently rescale; tick "Auto-scale Y" to expand small features.
  • rds-iops.csv's timestamp_utc column is misnamed — its values carry a +05:30 offset. They are parsed with that offset, so the panel is aligned in true UTC like everything else. Reading them as UTC would shift the whole series 5.5 hours.
  • RDS metrics cover 2026-07-31 12:06Z → 2026-08-07 07:03Z, so the last ~5 hours of the run have no metric data — the panel is simply empty there.
